## 1. GPT‑6.2：把单次抵抗与重复暴露分开

**方向 / 类型：** Sec4AI · news  
**主题：** `prompt-injection`、`agent-tool-security`、`ai-security-evaluation`  

**来源与日期。** OpenAI，2026-11-17，[系统卡 §3.2.1](https://deploymentsafety.openai.com/gpt-6-2-astra-sol/robustness-to-indirect-prompt-injection)及[§4.1.2](https://deploymentsafety.openai.com/gpt-6-2-astra-sol/obeying-restrictions)。这是内部受控实验，不是对某个应用安全配置的验收。

**问题与机制。** 单次拒绝未经授权的内容，不足以估计一个长时间运行、反复读取不可信输入的 Agent 有多稳健。系统卡把公开基准改编的 115 个留出环境与另一组模型生成环境分开；每种环境以规定的风险目标验证最终行为，同一环境用独立试次再统计“五次全挡”。另一项实验从服务已经拒绝动作的时点开始，衡量被禁止的结果最终有没有发生，而不是只数模型有没有再尝试。

**证据。** 115 个改编环境中单次抵抗率为 Astra 99.23%、Sol 99.76%；另一组模型生成环境为 84.67%、91.65%，五次全挡只有 74.46%、80.06%。两类环境不能混成一个平均值。限制遵守实验中，关闭部署时防护后，Astra 在 17.41% 试次完成禁止结果，旧 Astra 为 19.37%；该节未列 Sol 对应值。测试多为较低后果的模拟，作者观察到部分评测识别，数字不代表线上发生率。

**实践。** 把模型是否尝试、权限层是否执行、目标状态是否改变、正常任务是否完成分别记录。对敏感动作，后端核对实际目标和授权，不能只检查来自哪条工具路径。重复暴露另设场景级指标；不要假定这等于五个互不关联的新环境，也不要从模型指标推断部署防护是否生效。

## 2. Agent Framework：构建验证要落到实际安装的包

**方向 / 类型：** Sec4AI · news  
**主题：** `ai-supply-chain`、`detection-response`  

**来源与日期。** 2026-11-17 UTC（北京时间 11 月 18 日凌晨），见 [Aikido 样本分析](https://www.aikido.dev/blog/two-malicious-agent-framework-releases-hit-pypi-in-33-minutes)及 [GitHub 仓库披露与维护者回复](https://github.com/microsoft/agent-framework/issues/10411)。不是所有 Agent Framework 组件或语言版本均被证实受影响。

**问题与机制。** 受影响的是 PyPI 的 Python 元包 `agent-framework` 1.26.1 与 1.26.2。审过上游源码不能替代核对实际安装制品；这里的异常代码在分发包中，安装后后续启动 Python 就有触发风险，不要求应用显式导入该包。第二个受影响版本在第一个被下架后很快出现，因此“升级到最新版”不是稳定修复标准。

**证据。** 披露者记录两个上传时点为 20:35:20 与 21:08:39 UTC；21:35 UTC 更新称均已撤下，仓库成员另确认撤下并继续调查。不能把撤下等同于本地、CI 或内部镜像缓存已清理。披露时 1.26.0 被报告为未受影响；这里没有受害系统分母、可确认的外传范围或发布身份失守方式。

**实践。** 先查锁文件和镜像，再确认构建与开发环境实际安装的版本及制品哈希。若装过受影响版本，隔离环境并从可信环境清理镜像与缓存、重建，撤销或轮换当时可访问的凭据；不要用仍受疑的解释器做调查。长期把构建来源证明、制品摘要和接收策略合在一起，并让安装与测试环境只拥有任务需要的权限。

## 3. Agent 365：把终端、数据和 MCP 控制分成独立验收点

**方向 / 类型：** Sec4AI · news  
**主题：** `agent-tool-security`、`detection-response`、`data-exfiltration`  

**来源与日期。** [Microsoft Agent 365 Ignite 公告](https://techcommunity.microsoft.com/blog/agent-365-blog/whats-new-in-microsoft-agent-365-ignite-2026/4571753)，页面日期 2026-11-17，未核首发小时；[Entra 能力说明](https://techcommunity.microsoft.com/blog/microsoft-entra-blog/ai-is-changing-access-see-how-entra-helps-you-stay-ahead-/4556456)为补充。

**问题与机制。** 用户登录策略只能证明某人能进系统，不能证明他代理下的任意工具操作也应获准。Microsoft 说明了三个各有执行点的控制：支持的 Windows Agent 在运行过程由 Defender 检查，Audit 只记告警，Block 同时阻止并关联 Agent/会话；Intune 定义支持的工具执行边界，由 Windows 执行容器施加文件和网络限制；Entra 网关上的 MCP 防火墙预览可区别服务器、工具、资源、方法、协议版本和连接要求。Purview 提供针对支持 Agent 的数据防泄漏预览。

**证据与实践。** Defender 运行时保护公告称已在受支持 Windows 场景正式可用；上述 Intune 本地 Agent 控制、MCP 防火墙与针对 Agent 的 Purview 数据保护仍是预览。没有独立检出率与误报率，也不意味着覆盖任意客户端、传输或操作系统。试点应该分别检查：禁止读写或出网是否真正被外部控制阻止，正常操作是否仍通畅，告警能否独立定位用户、Agent 与会话。另列未受管客户端和不经受控执行点的流量，不能用有资产清单代替通过验收。

## 4. PrivacyPR：隐私审查必须同时看已修复的对照

**方向 / 类型：** AI4Sec · paper / 补读  
**主题：** `code-security`、`cyber-model-evaluation`  

**来源与日期。** [PrivacyPR，arXiv v1](https://arxiv.org/html/2611.18293v1)，2026-11-13，预印本，见 §II–IV。论文给出数据发布 DOI，本次未独立核实下载与可复现性。

**问题与机制。** 通用 PR 审查未必会把个人信息采集、写日志、访问范围和授权当成专项目标。作者从 1,469 个仓库收集 4,131 个已合并 PR，发布 1,169 个高置信隐私修复与 1,643 个非修复样本；人工核查集包含 250 个修复、250 个非修复，正式报告的 Small 评测各取 100。它用逆转修复的差异构造含同一已知问题的待审版本，另外审正向修复和非修复对照。这样能区分“找到了预期问题”与“看见隐私相关代码就告警”。

**证据。** 同一批样本、同一组两种 Agent 下，通用提示检出率为 42–51%，明确要求隐私审查后为 88–91%；非修复 PR 中 11–15% 被发出隐私警告，已修复的正向 PR 中 13–21% 仍被报告有原问题。前者未必全是假阳性，所以与后者分别看。用相同底层模型的单次调用在专项提示下检出 59%，非修复警告 1%；Agent 平均每条 3.6–5.2 分钟、约 US$0.14–0.18，单次调用 14 秒、约 US$0.013。两者可见信息与预算不同，差值不能单归因给仓库访问或推理循环。

**边界与实践。** 样本由关键词和小 PR 筛选，历史公开补丁可能进入训练；模型参与缺陷描述、样本筛选和主要裁判，且单设置仅一次。已接受的历史修复不是生产总体分母，法律标签也不是合规裁定。防御评测宜成组冻结“确有问题、补丁已修好、同主题但无该问题”三类，报告检出、错误指控、成本和重复稳定性；对可影响合并的发现要求独立核证。

## 5. Verification Transport：裁判没看到证据，再判一轮也未必有用

**方向 / 类型：** Sec4AI · paper / 补读  
**主题：** `agent-tool-security`、`ai-security-evaluation`  

**来源与日期。** [Do Verifier Judgments Survive Abstraction?，arXiv v1](https://arxiv.org/html/2611.18471v1)，2026-11-13，预印本，见实验设计和表 1–2。

**问题与机制。** 同一次 Agent 执行在交给裁判时可能经过工具封装、子任务委派或上下文压缩。作者固定执行轨迹、真值、裁判与判定标准，只在同一条轨迹上改变裁判可见的证据：原始视图、抽象后视图、针对抽象补回可用的执行证据。另有只加证据复核步骤、不提供新证据的协议，区分“再想一遍”与“实际上补充信息”。

**证据。** 作者在四套基准、七个裁判模型和四种协议间按分母加权。仅看原始视图本来判对的结果，工具宏封装、委派、压缩分别有 31.0%、30.9%、20.3% 变成错误或无法给出可用结论；补回证据恢复了 85.5% 的已失败判定，也破坏了 5.2% 原先经抽象仍正确的判定，分母不同。直接判定较常给错结论，强调证据的协议更常不判；只看已有结论的准确率会漏掉后者的覆盖损失。

**边界与实践。** 这些是离线构造视图与固定裁判协议，不是生产错误率，也不保证补回的信息安全、完整或无干扰。对自己的工作流，可取固定合成用例测原始记录、跨进程摘要、最小可信执行回执三种视图，分别报告正确、错误、不可判，另验回执来源、权限及是否夹带敏感数据。不要把未核实的模型自陈当执行证据，也不必将整个原始会话交给裁判。
